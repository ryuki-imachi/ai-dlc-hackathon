## 1. プロダクト Intent

### 1.1 1行 Intent（外向き / PR コピー）

> **「マカセル — 任せ続けたら、もう戻れない。」**（2026-05-09 確定）

確定理由:
- 「任せ続けたら、もう戻れない」が **段階 1（任せる）→ 段階 2（拡大）→ 段階 3（戻れない）** の旅路と直結
- 「もう戻れない」が「人をダメにする」テーマを 14 文字でストレートに射抜く
- ペルソナ（マジメ・完璧主義タイプ）の自尊心崩壊の感情曲線にもハマる

採用しなかった候補メモ（参考）:
- 「全部、マカセル。」 — シンプルだがダメさが伝わらない
- 「マカセル。やがて、何もしなくなる。」 — 重め
- 「マカセル時代。」 — トレンド感だが情緒不足
- **「サボれ。世界が、勝手にがんばる。」**（タレカツさんレビュー D「AI → API → 人」を踏まえた候補。最有力）
- 「マカセル。世界が、勝手にがんばる。」 — D 論点直撃のサブコピー候補（応募文・プレゼンの文中で活用余地あり）

### 1.2 内部 Intent（プロダクトとしての作用機序）

> **「やらなくていい、を毎朝教えてくれる AI（八木案）」を起点に、
> 助けるフリして判断・実行を「肩代わり」または「他者へのお願い」として外注させ、ユーザーをダメにする」**

「人をダメにする」テーマへの回答 = **判断する力・実行する力・他者と交渉する力を AI に取り上げられる**。

> **重要**: 「サボる」は **ブッチ（無断不参加）ではなく** 、AI が **適切な相手に依頼・移譲・調整する** 形を取る（タレカツさんレビュー A 論点への対応）。
> ユーザーは「自分で頼みに行く心理的ハードル」と「依頼文を書く労力」を AI に肩代わりさせる。
> 結果として、ユーザーは「自分で人にお願いする力」を失っていく。

これにより、SNS路線（提案書 03-proposal.md）が依存していた「承認欲求の駆動」「現実遮断」「サボリ仲間との比較」をすべて捨て、
**1人 × AI の閉じた感情体験** に振り切る。

#### 1.2.1 二層構造: 「ユーザーをダメにする」の裏側で起きていること

タレカツさんの追加レビュー（[`after.md`](../../../pre-ai-dlc/04-brainstorm/team/after.md)）から汲み取った重要な視点。

```
[表層]                        [裏層]
ユーザー  ──── マカセル ────▶  AI Agent ──── API ────▶  他者（同僚 / 上司 / 取引先）
「サボる」と頼む              【3 タイプの代行アクション】
                              ① 他者への依頼文（誰かにお願い）★中心
                              ② 断り文 / 欠席連絡（自分が降りる）
                              ③ 延期・スケジュール調整
```

- 表層では **ユーザー × AI の閉じた体験**: 「私は AI に頼んだだけ」
- 裏層では **AI が API 経由で他者を間接的に動かしている**: メールが届く、**他のメンバーにタスク依頼が飛ぶ**、カレンダーに欠席通知が入る、相手の予定が変わる
- 「サボる」の **中心は「他者への依頼」** に置く（タレカツさん論点 A 対応）。ブッチではなく、AI が代わりに「お願い」する設計にすることで、社会的に成立する形でユーザーを依存させる
- ユーザーは **「自分で人にお願いする心理的ハードル」と「依頼文を書く労力」を AI に外注する** → 結果として「自分で頼む力」を失っていく
- 同じ AI を相手側も使い始めると **「依頼と再依頼の押し付け合い」が連鎖**し、社会全体で誰も自分で仕事をしなくなる悪夢（タレカツさん論点 B）

この **「AI → API → 人 で間接的に AI が人を操作する構図」** が「人をダメにする」の真の射程。デモ・プレゼンの強力なネタ。
ハッカソンでは **倫理的にホワイトハット実装**（モック宛先 / ディスクレーマー）に留めつつ、**コンセプトとして振り切る**。

### 1.3 採用ベース案

[`pre-ai-dlc/04-brainstorm/team/yagi.md`](../../../pre-ai-dlc/04-brainstorm/team/yagi.md) の「サボってよいリスト」案を起点に、**2 段階の旅路** として体験を設計する。
（八木案の段階 1〜3 のうち、**真ん中の「人間が承認するステップ」を省略**。「マカセル — 任せ続けたら、もう戻れない。」の Intent を真っ直ぐに体現するため）

| 段階 | 内容 |
|---|---|
| **段階 1（最初から自律）** | AI が **サボリ判定 → 代行アクション（依頼 / 断り / 延期）の自動送信** までを承認なしで一気に実行。ユーザーは事後に代行ログを見るだけ |
| **段階 2（戻れない境地）** | ユーザーは **代行ログすら見なくなる**。AI が動いていることすら意識しない。秘書に丸投げの境地 |

**MVP（5/30 予選）では段階 1 を実装、決勝（6/26）で段階 2 の境地を見せる**。

> **設計変更（2026-05-09）**: 当初は 3 段階構造（リスト提示 → 人間が承認して代行 → 見ない）で設計していたが、「いきなり自律でいい」とのユーザー判断により 2 段階に再構成。
> 旧段階 2 の「下書き生成 → 人間承認」のフローは削除し、AI が承認なしで自律実行する形へ。
> この変更によって「人をダメにする」の振り切りが強化される一方、自律実行の暴走リスクには明示的なセーフガードが必要（§5.5・§8 参照）。

## 3. ペルソナ（1人固定: マジメ・完璧主義タイプ）

> 追加質問の回答に基づき確定。

### 3.1 プロファイル

| 項目 | 内容 |
|---|---|
| 名前 | 鈴木健太（仮、変更可） |
| 年齢 | 28〜32 歳前後 |
| 職業 | IT 企業のプロダクトエンジニア / PdM など、自分の判断で動く職種 |
| 性格 | **マジメ・完璧主義**。自分でやりたい意欲が強く、品質に妥協したくない |
| 自己投資傾向 | Notion で生活管理、技術書を読む、ランニング・サウナ、瞑想アプリを試す |
| AI に対する初期姿勢 | 「効率化ツールとして使う」前向きさはあるが、「自分でやれることは自分でやりたい」抵抗もある |
| デバイス | スマホ（iPhone/Android）、PC（Mac/Windows） |

### 3.2 ジョブ理論（TASKILL が刺さる構造）

| 軸 | ジョブ | TASKILL がどう刺さるか |
|---|---|---|
| 機能的 | 効率化したい、生産性を上げたい、無駄を省きたい | AI が代行することで「時間が浮く」 |
| 感情的 | 「自分はちゃんとやれる人間でありたい」自尊心を保ちたい | 最初は「ちょっとだけ任せる」、徐々に「これくらいなら任せていい」が広がる |
| 社会的 | デキる人・効率厨として認知されたい | 「最新の AI を使いこなしている」と外向きの説明ができる |

### 3.3 TASKILL との関係性（時間軸）

1. **導入期**: 「便利になるなら」と前向きに導入。タスク 1 件だけ任せてみる
2. **拡大期**: 任せる範囲が日に日に広がる。AI Agent が獲得した skill が増えていく
3. **依存期**: 気付かないうちに、自分で判断する機会が消えている
4. **無能化**: AI なしでは決められない、書けない、断れない状態になる

> このペルソナの旅路を **MVP デモの 3 分** ではなく **デモの背景ストーリー（応募文・スライド・決勝ナラティブ）** として用いる。
> 単一プレゼン内で全員が感情曲線を辿る必要はない（NFR-DEMO-5 とも整合）。

## 4. 機能要件（FR）

### 4.1 段階 1: 最初から自律（**MVP 必須**）

AI が **サボリ判定 → 代行アクション送信までを承認なしで一気通貫** に行う。
ユーザーは「カレンダーを連携する」「事後にログを見る」「（任意で）独り言で意図を伝える」だけ。

| ID | 機能 | 説明 |
|---|---|---|
| FR-1.1 | Google カレンダー / Gmail 連携 | 初回のみ OAuth で連携。日次でスケジュール / メールを取得 |
| FR-1.2 | サボリ判定 AI | カレンダー / Gmail から「今日サボってよいこと」を AI が抽出 |
| FR-1.3 | **自律代行実行**（核） | サボリ判定された項目に対し、AI が **ユーザー承認なし** で 3 タイプの代行アクションを送信: ①**他者への依頼**（中心、タスク移譲）/ ②断り・欠席 / ③延期・再調整 |
| FR-1.3-A | サボリ・代行ログ表示 | アプリ画面で「今日 AI が誰に何をしたか」を **事後** に確認できる。チェック / 達成判定 / 編集はできない |
| FR-1.4 | **音声入力での意図伝達（任意の補助）** | 「明日の朝会、いらない」「メール、全部任せた」など **独り言レベルの発話** で AI に追加指示。発話なしでも AI は自律的に動くが、発話があれば判断を補強する |
| FR-1.5 | **テキスト入力での意図伝達（サブ）** | 音声を出せない環境（オフィス・電車内）向けのフォールバック。AI は同じく追加指示として受け取る |
| FR-1.6 | 操作の最小化 | チェック / 達成判定 / 振り返り入力は **持たない**。ユーザーはログ閲覧と音声 / テキスト指示のみ |
| FR-1.7 | **「後押し」メッセージ**（タレカツさんレビュー C 対応） | ログ表示の各項目に「なぜそれをサボってよいか」の根拠を短く併記。マジメな鈴木健太が「いやいや本当にサボっていいの？」と引き戻されないよう、AI が背中を押す。例: 「この会議、議事録だけで十分。田中さんに代理出席を依頼しました」 |
| FR-1.8 | **暴走防止セーフガード** | 自律実行の対象を明示リストに限定（特定種類のイベント / 特定送信先のみ）。ハッカソンスコープでは **モック宛先のみ**（実在の第三者には送信しない） |
| FR-1.9 | **緊急停止** | 設定画面に「マカセル一時停止」スイッチ。ON にすると自律実行が止まる |

> ⚠️ **通知は実装しない**（レビュー v1 反映）: アプリへの依存を避けるため、プッシュ通知や音声通知でユーザーをアプリへ呼び戻さない。
>
> ⚠️ **下書き生成 → 人間承認 → 送信、というフローは持たない**（2026-05-09 設計変更）。AI は内部で下書きを生成しつつ、そのまま送信まで実行する。承認 UI はゼロ。

#### 4.1.x 補足: Slack 連携（任意）

Slack でのタスク依頼 DM / 断り返信を MVP 内に含めるかは時間次第。優先度低。

#### 4.1.y 補足: 自己フィードバック / Agentic Skill 化（**コアではない / 余裕があれば**）

決勝で技術深さを見せる文脈で、AI Agent の自己フィードバックループ・Agentic Skill 化を組み込む余地はある（実装やデモ表現の余裕がある場合）。
ただし **コアコンセプトではない**。MVP 段階で追求する必要はない。Application Design / Construction で実装余力に応じて判断する。

### 4.2 段階 2: 戻れない境地（**決勝向け / MVP では UX 演出**）

| ID | 機能 | 説明 |
|---|---|---|
| FR-2.1 | サボリ・代行ログの自動隠蔽 | AI が成功した代行は時間経過でログから視界から消えていく。ユーザーは「どう動いているか」を意識しなくなる |
| FR-2.2 | 「見ないリスト」体験 | リストもログも存在するが、ユーザーは開かなくなる。マカセル先生に丸投げの境地 |
| FR-2.3 | 30 日後の利用者ストーリー | 決勝デモで「30 日後、ユーザーは TODO を見ていない / N 件の依頼を AI が代わりに送っていた」演出を見せる |

> 段階 2 は **実装** よりも **UX の表現方法と語り口** が肝。
> MVP では FR-2.3 の演出データのみ用意し、本実装は決勝までに行う。

## 5. 非機能要件（NFR）

### 5.1 デモ表現の要件（最優先）

> ⚠️ レビュー v1: 「天才と思わせる必要があるかは怪しい」「ペルソナの感情曲線に引っ張られすぎ」のフィードバックを受けて再定義。

3 分プレゼンで以下を達成する具体要件:

- **NFR-DEMO-1**: ハッカソンテーマ「人をダメにする」が **15 秒以内に伝わる** ように、Intent コピーを冒頭に出す（コピーはプロダクト名確定後）
- **NFR-DEMO-2**: 「助けるフリしてダメにする」二重構造を 1 シーンの実演で示す。AI に頼んだ結果、ユーザーが自力で何かをする機会が消えていることが観客に伝わる
- **NFR-DEMO-3**: アプリ単体だと動きが少ないため、**裏で AI が何をしているか** を映像 / ログ / 可視化画面で見せる演出を必ず組み込む（後述 8 章リスク）
- **NFR-DEMO-4**: 演出は **アプリへの依存を促さない**。プッシュ通知や音声出力で「アプリを使わせる」シーンは出さない（プロダクトコンセプトと矛盾するため）

> 感情曲線・ペルソナ依存の演出は **避ける**。プロダクトの作用機序（AI に任せたぶんユーザーが何もできなくなる）そのものをデモのコアにする。

### 5.2 デプロイ・データ

| 項目 | 値 |
|---|---|
| リージョン | ap-northeast-1（東京）一本 |
| データストア | DynamoDB |
| 保存期間 | 30 日（TTL） |
| PITR | OFF |
| バックアップ | なし（ハッカソンスコープのため） |

> ap-northeast-1 で Claude Sonnet 4.6 が利用可能（レビュー v1 で確認済）。Haiku 4.5 の利用可否は Application Design で詳細確認する。

### 5.3 コスト

- 明示的な月額閾値は設定しない
- ただし、ユーザー単独 × 日次数回の処理を超える設計（NPC 量産・タイムライン Fan-out 等）は採用しない
- ハッカソンクレジット内で完結する想定

### 5.4 セキュリティ・プライバシー

- 取得対象は **本人の Google カレンダー / Gmail のみ**（他者発の通信は触らない）
- メッセージ本文の Bedrock 送信時は **必要最小限のフィールドのみ**
- 学習利用 OFF（Bedrock 設定で明示）
- プロンプトインジェクション対策は Construction で詰める（保留）

### 5.5 倫理・ガバナンス

- 「人をダメにする」テーマだが、**実装としてはホワイトハット寄せ**（依存設計はしない、退会は1クリック）
- 詳細なリーガルドキュメント整備は Construction フェーズで実施（Q-G1 D 選択）
- **「完全自律」設計に伴う追加リスク**（2026-05-09 設計変更）:
    - 人間承認を省いたため、**AI の判断ミスがそのままアクションになる**
    - 対応: ①自律対象を明示リストに限定（FR-1.8）/ ②モック宛先のみ（実害遮断）/ ③緊急停止スイッチ（FR-1.9）/ ④代行ログを事後確認可能に（FR-1.3-A）
    - 本番運用化は Construction フェーズの倫理ドキュメントで設計（ホワイトリスト方式 / 信頼度 / 監査）
- **「AI → API → 人」の構図に伴う倫理リスク**（タレカツさんレビュー）:
    - **論点 A 自覚低下**: ユーザーが「サボった自覚」を持たないまま、周囲には実害（ブッチ）が残る → MVP は **モック宛先のみ** で実害を遮断、本番化は将来の倫理ドキュメントで設計
    - **論点 B 押し付け合いの連鎖**: 相手側も同じ AI を使うと「言いくるめの押し付け合い」が連鎖 → ハッカソンスコープでは **単一ユーザー想定** で回避、複数ユーザー世界の倫理は Construction で言及するのみ
