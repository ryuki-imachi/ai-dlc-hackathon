## 0. エグゼクティブサマリー

「**人をダメにする**」テーマに対して、私たちは **「サボリスト」** を提案する。

> **サボったら褒められる、現実遮断SNS。**
> スマホを AI が制圧して仕事の通知を物理ミュートし、サボった日数・回避したタスク数を連続記録としてランキング化。AI が「今日もよくサボれました」と褒める。

「やらないことの正当化」「甘やかしで溺れさせる」「現実から遮断」の **三軸ハイブリッド**で、Larry Wall の言う「怠惰」を文化資本に変える振り切った設計。AI-DLC の Unit 分解が綺麗にハマるため、書類審査・予選・決勝のすべてのフェーズで戦える。

## 2. なぜ「サボリスト」か — 審査観点へのマッピング

### 2.1 ビジネス意図（Intent）の明確さ ★★★★★

「**怠惰の合理化を、SNS の承認欲求で駆動する**」という1行の Intent に集約できる。
Inception フェーズで Intent ドキュメントを書く際、ペルソナ（残業疲れの社会人）・課題（働きたくないが、サボることに罪悪感がある）・価値（AI による代行 + 仲間からの称賛で罪悪感を消費する）が綺麗に分解できる。

### 2.2 創造性とテーマ適合性 ★★★★★

| 「ダメにする」軸 | 採用機能 |
|---|---|
| やらないことの正当化 | AI 自動返信代行（運営例「無限先延ばしくん」を内包） |
| 甘やかしで溺れさせる | サボった日数を AI が褒める |
| 現実から遮断 | 通知ミュート + 仕事系アプリの非表示 |

運営例の「無限先延ばしくん」「行動全部決定 AI」を **1 つのプロダクトに統合**し、SNS 性で増幅させた構造。テーマど真ん中に振り切っている。

### 2.3 Unit 分解の適切さ ★★★★★

6 Unit に綺麗に分解可能（[`concept.md`](./concept.md) に詳細）：

1. **通知ミュート Unit** — 端末通知を分類して仕事系を抑制
2. **自動返信代行 Unit** — Slack/Gmail/LINE の受信に AI が一次返信
3. **サボリ計測 Unit** — 連続未対応日数・回避タスク数の集計
4. **タイムライン Unit** — サボリ仲間の活動配信・いいね・ランキング
5. **AI 称賛 Unit** — 褒めコメント生成・MVP 選定・煽り
6. **退会防止 UX Unit** — 依存をデザインで強化

各 Unit ごとに Intent → 仕様 → 実装 → 検証のループが独立して回せる。**Unit of Work 計画書が厚く書ける**のが強み。

### 2.4 ドキュメントの品質 ★★★★★

`awslabs/aidlc-workflows` のテンプレートに沿って `aidlc-docs/` 配下に成果物を整える前提。
コンセプト自体が明快なので、ユーザーストーリーが具体的に書ける（後述）。

### 2.5 アイデアと技術のバランス ★★★★☆

| 軸 | 評価 |
|---|---|
| アイデアの強さ | 共感度・背徳感・デモ映え揃って強い |
| 技術の深さ | Bedrock（Sonnet 4.6 / Haiku 4.5）+ AgentCore（Runtime / Gateway）+ Polly + Lambda + DynamoDB を多重活用 |
| 過剰技術リスク | 通知ミュートを端末ネイティブで実装すると重い → MVP では Slack/Gmail 側のミュートに絞る、で回避 |

## 3. AI-DLC Inception フェーズ成果物計画

書類審査向けに 5/10 までに以下を `aidlc-docs/` 配下に揃える。

### 3.1 要件分析（`aidlc-docs/inception/requirements.md`）
- ペルソナ：残業に疲弊した社会人、罪悪感持ちのサボリ志望者
- ユーザーが置かれた現状の課題（働きたくない × サボれない）
- 機能要件 / 非機能要件
- 制約（プライバシー、企業 Slack の利用ポリシーなど）

### 3.2 ユーザーストーリー（`aidlc-docs/inception/user-stories.md`）

例：
- **US-01**：ユーザーとして、Slack で上司から催促が来ても AI が断り文を返してくれることで、罪悪感なく無視できる
- **US-02**：ユーザーとして、サボった日数が連続記録として可視化されることで、達成感を得られる
- **US-03**：ユーザーとして、サボリ仲間のタイムラインが流れることで、自分だけがダメではないと安心できる
- **US-04**：ユーザーとして、AI が「今日のサボラー MVP」を選定し褒めてくれることで、サボることが報われる体験を得られる

### 3.3 アプリケーション設計（`aidlc-docs/inception/architecture.md`）
- C4 モデルでコンテキスト → コンテナ → コンポーネント図
- AWS アーキテクチャ図（Lambda + DynamoDB + Bedrock + AgentCore + Polly）
- データモデル（ユーザー、サボリイベント、投稿、いいね、ランキング）

### 3.4 Unit of Work 計画（`aidlc-docs/inception/unit-of-work.md`）
- 上記 6 Unit ごとに Intent / 受け入れ基準 / 依存関係 / 工数見積もりを記載
- マイルストーン：MVP（予選 5/30）/ Final（決勝 6/26）でどの Unit がどこまで実装されるか

### 3.5 Optional 成果物
運営ヒントの「Optional フェーズもやるとスキルが見せられる」に応じて、余裕があれば：
- リスク分析（プライバシー、倫理面）

## 4. MVP スコープ（5/30 予選向け）

予選では **1回以上 Construction を完了した MVP のデモ** が求められる。3 分で「ダメさ」が一発で伝わる構成にする。

### 4.1 MVP に必須の Unit
- ✅ **Unit 2: 自動返信代行**（Slack のみで OK）
- ✅ **Unit 3: サボリ計測**
- ✅ **Unit 4: タイムライン**
- ✅ **Unit 5: AI 称賛**

### 4.2 MVP では割愛
- ⏸️ **Unit 1: 通知ミュート**（端末側実装はコストが重い、デモはモックでOK）
- ⏸️ **Unit 6: 退会防止 UX**（決勝までに作り込み）

### 4.3 デモシナリオ（3分）
1. (0:00) ユーザーが Slack で「明日の朝会、出れないかも」と独り言
2. (0:30) AI が上司に体調不良連絡を自動送信、Slack のタスクに「【明日やる】」リネーム
3. (1:00) サボリストアプリ画面に切り替え、タイムラインに「@you が朝会を AI にバックレさせた」が投稿
4. (1:30) 仲間からの「ナマケ」（いいね）が飛んでくる
5. (2:00) AI が「今日のサボラー MVP」として選出、Polly の優しい音声で「今日もよくサボれました」
6. (2:30) サボリ連続記録が「47日」に更新、ランキング上昇
7. (3:00) 締め：「あなたはもう戻れません」

## 5. 決勝スコープ（6/26 AWS Summit Japan）

「**AWS 上で動作するデモ**」が要件。MVP からの差分で見せ場を増やす。

### 5.1 追加機能
- **Unit 1: 通知ミュート**（モバイルアプリ実装、または PWA + 通知 API）
- **Unit 6: 退会防止 UX**（深く隠された退会フロー、AI による引き留め）
- **複数ユーザー間のタイムライン**を本格運用（事前にダミーユーザーを仕込む）
- **AgentCore Memory** で各ユーザーの「サボリ履歴」を記憶し、パーソナライズされた褒めを生成

### 5.2 「アイデアと技術のバランス」を見せるための技術深化
- AgentCore マルチエージェント（返信エージェント / 称賛エージェント / ランキング集計エージェントの協調）
- Bedrock Knowledge Base にユーザー過去ログを蓄積し RAG で「あなたらしいサボリ言い訳」を生成
- リアルタイム配信（AppSync Subscriptions または WebSocket API Gateway）

### 5.3 AI-DLC チャンピオンメンタリング
- 希望制で活用。Inception → Construction の遷移、Optional フェーズの取り組みについてアドバイスをもらう

| テーマが過激すぎて倫理面で減点 | 中 | 「ネタとしての振り切り」をコンセプトドキュメントで明文化、デモも笑える文脈に |

| サボリ仲間のタイムラインが空でデモが寂しい | 中 | ダミーユーザーのサボリ投稿を事前に仕込む |
| 5/10 締切まで残り3日（今日 5/7）| 高 | 応募文面と Intent ドキュメントを最優先で 5/8 までに完成 |

## 8. 応募フォーム文面ドラフト

> 応募フォームには「アプリ開発実績」と「開発予定のユースケースおよびアプリの構想」の 2 設問（各 800 字以内）があるが、運営からは**開発実績は審査で考慮しない**と聞いているため、構想欄に注力する。

### 8.1 開発予定のユースケースおよびアプリの構想（800字以内）

**ドラフト案**：

> 私たちが提案するのは「サボリスト」、サボったら褒められる現実遮断 SNS です。スマホに AI が常駐し、Slack / Gmail / Calendar の仕事系通知を物理的にミュート。届いた催促や招待には AI が代理で返信し、ユーザーは一切現実と向き合わなくて済みます。代わりに画面に流れるのは「サボリ仲間」のタイムラインだけ。「@田中が連続37日のサボリMVP達成」「@鈴木が3件の会議をAIにバックレさせた」といった投稿が並び、「ナマケ」（いいね）が飛び交います。AIは毎日「今日のサボラーMVP」を選定し、Polly の優しい音声で「今日もよくサボれました」と褒めてくれます。
>
> 「人をダメにする」という設計思想は、Larry Wall の言う「怠惰」を SNS の承認欲求で駆動するという、極めて意図的な振り切りです。やらないことの正当化（AI 代行）・甘やかしで溺れさせる（AI 称賛）・現実から遮断（通知ミュート）の三軸を 1 プロダクトに統合しました。
>
> 技術スタックは Amazon Bedrock（Claude Sonnet 4.6 / Haiku 4.5）+ AgentCore Runtime / Gateway + Lambda + DynamoDB + Polly。AI-DLC では Inception フェーズで Intent を「怠惰の合理化を承認欲求で駆動する」と定義し、6 つの Unit（通知ミュート / 自動返信 / サボリ計測 / タイムライン / AI 称賛 / 退会防止）に分解。MVP では中核 4 Unit を予選で動かし、決勝では端末ネイティブのミュート機能と AgentCore Memory による個別最適化を加えて完成させます。
>
> ハッカソンの審査観点であるアイデアと技術のバランス、Unit 分解の適切さの両方を満たす構造を持つ、本気で振り切った「人をダメにする」プロダクトです。
